# Closed toolpath API dictates Fusion plugin strategy

Commercial multi-axis CAM in 2026 is a mature, consolidated market. The real work in 5-axis is no longer about adding surface strategies. It is about **automatic tool-axis management**: tilting a 3-axis pattern into a collision-free 5-axis path, mixing indexed and simultaneous moves, keeping the shank and holder clear, and smoothing rotary motion. hyperMILL, NX, PowerMill, Tebis and Mastercam all shipped improvements there in 2025–26. Autodesk Fusion already covers most of the functional checklist. Core Fusion (about **$680/yr**) includes 2.5D, 3-axis, 3+1/3+2 positional milling, machine simulation and editable JavaScript posts. The Manufacturing Extension (about **$1,465/yr**) adds everything simultaneous: Rotary, Swarf, Multi-Axis Contour and Flow, 5-axis Steep & Shallow, Multi-Axis Clearing, collision-avoidance tilting, toolpath editing and hole recognition. Autodesk filled several historical multi-axis gaps in 2026 alone. The constraint that matters most for the plugin is architectural. The Fusion `adsk.cam` API can create, parameterize, generate and post *native* operations. It **cannot register a new toolpath strategy, and it cannot inject externally computed toolpaths as native operations**. So every design falls into one of three shapes: an orchestrator of native strategies, a supplier of drive geometry to native strategies, or a parallel engine with its own simulation and post. On build versus license: the plugin is open source under **MIT OR Apache-2.0**. That lets it absorb permissive code (Kiri:Moto, MIT). It can use LGPL libraries (OpenCAMLib, OCCT, FreeCAD parts) only as separate, dynamically linked, replaceable dependencies. GPL projects (Fabex, jscut, CAMotics, PyCAM) can serve only as references for clean-room reimplementation. **No production-quality open 5-axis toolpath library exists**, so the 5-axis core must be built in-house. The Fusion API and Autodesk's `.cps` post engine remain unavoidable proprietary dependencies. ModuleWorks (the only shelf-ready 5-axis engine, partly owned by Autodesk) and MachineWorks are closed fallbacks, not defaults. The least crowded openings are these:

- collision-free automatic tilting that users can understand;
- affordable continuous 4-axis and small-machine 5-axis with correct kinematics;
- application packs (port, impeller, blade) that Fusion appears to lack;
- G-code-level verification.

Automated 3-axis and 3+2 programming should be avoided, because Autodesk, Toolpath and CloudNC already occupy it.

## A full multi-axis CAM is fourteen functions deep, and toolpaths are one of them

A plugin designer needs a vendor-neutral map, because Fusion already supplies most of the pipeline. The pipeline is the same for every vendor: **setup/WCS → stock → fixtures → tools and holders → feeds and speeds → templates and feature recognition → toolpath operations → linking → simulation and verification → post → documentation → probing**. The steps that cost shops the most time are not toolpath generation. Posts that "almost fit" a controller force hand-editing of every program ([MecSoft](https://mecsoft.com/blog/why-many-shops-regret-their-cam-software-purchase)). Badly configured 5-axis posts cause axis-limit, retract and collision errors. The recommended 5-axis sign-off chain is CAM machine simulation followed by controller-side G-code verification ([industrialmonitordirect, low-authority](https://industrialmonitordirect.com/de/blogs/knowledgebase/5-axis-programming-time-estimation-hypermill-best-practices)). Kinematics affect correctness, not just appearance. On the Pocket NC V2 trunnion, the WCS must match the B-table orientation or the code fails ([Pentamachine](https://pentamachine.atlassian.net/wiki/spaces/PNFUR/pages/1732739077/V2+Series+Work+Coordinate+System+Tutorial+Kinetic+Control)).

The **shared core** sits under every simultaneous family. Its parts are:

- tool-axis control modes: fixed, normal, lead/lag + lean, to/from point, to/from curve, interpolated vectors, limit cones;
- collision avoidance across shank, holder, fixture and machine head;
- tool-axis smoothing;
- singularity handling near the rotary pole;
- choosing between inverse-kinematics branches;
- linearization and inverse-time feed.

Fusion's tool-axis vocabulary is From/To Point, From/To Curve and lead/lean ([Fusion help](https://help.autodesk.com/cloudhelp/ENU/Fusion-CAM/files/MFG-REF-3D-STEEP-SHALLOW-TOOL-AXIS-MODE.htm)). Hurco ([blog](https://blog.hurco.com/blog/bid/242006/5-axis-programming-understanding-tool-axis-and-collision-controls)) and Mastercam ([CTE](https://ctemag.com/?p=109914)) describe the same concepts in vendor-neutral terms. The academic basis is configuration-space orientation planning ([Springer IJAMT](https://link.springer.com/article/10.1007/s00170-023-12031-7)). The standard survey is Lasemi, Xue & Gu (CAD 2010), confirmed only through a secondary reference list ([Manufacturing Review](https://mfr.edp-open.org/articles/mfreview/ref/2018/01/mfreview170023/mfreview170023.html)). The same core breaks down by machine class: table-table trunnions (Pocket NC, Haas UMC-class), head-table, and head-head. Each class needs the CAM or the post to handle RTCP/TCPC versus non-RTCP output. The per-controller codes are [BK]: Fanuc G43.4/G68.2/G93, Siemens TRAORI/CYCLE800, Heidenhain M128/PLANE SPATIAL, Haas G234/G254.

## Four owners and one kernel supplier shape the commercial market

Ownership consolidated sharply after 2021. **Sandvik** owns Mastercam (acquired 30 Sep 2021; ~270,000 licenses at the time, now claiming 450,000+ installs) and Cambrio (GibbsCAM, Cimatron, SigmaNEST) ([Sandvik](https://www.home.sandvik/en/news-and-media/news/2021/09/sandvik-completes-the-acquisition-of-leading-cam-software-company-cnc-software-inc.-creators-of-mastercam); [MMS](https://mmsonline.com/news/sandvik-acquiring-cadcam-company-cambrio)). **Hexagon MI** owns ESPRIT EDGE, Edgecam, WorkNC, VISI and NCSIMUL. Its 2026 Octave spin-off did **not** take the CAM products ([Hexagon](https://hexagon.com/company/newsroom/press-releases/2025/octave-unveiledhexagon-reveals-name-for-potential-2026-company-spin-off)). **Siemens** has NX CAM. **Autodesk** is consolidating onto Fusion:

- HSMWorks was removed from new subscriptions on 25 Mar 2025 and reaches end of life on 25 Mar 2028 ([Autodesk](https://autodesk.com/products/hsmworks/overview)).
- The free Inventor CAM Express and HSMXpress are frozen ([Autodesk](https://www.autodesk.com/products/inventor-cam/free-download)).
- Users describe PowerMill 2026 as a stability release ([forum](https://forums.autodesk.com/t5/powermill-forum/powermill-2026/m-p/13886787)).
- CAMplete reportedly reaches end of sale on 7 Jun 2026, per a reposted notice **[unverified]** ([mastercamforums](https://mastercamforums.com/forum/index.php?msg=111194)).

Two common misconceptions need correcting. CAMWorks remains with HCLSoftware and did not become Cambrio ([HCL](https://www.hcl-software.com/news/23-1-26-hclsoftware-releases-swiss-machining-in-hcl-camworks-2026)). CAMplete is Autodesk-owned, not Hexagon ([Autodesk](https://www.autodesk.com/products/camplete/features)).

Underneath the brands, **ModuleWorks says more than 60% of leading CAM vendors use its 5-axis component** (vendor claim; [ModuleWorks](https://www.moduleworks.com/software-components/toolpath/)). Its partner page lists Autodesk Fusion, Mastercam, Siemens, PTC, Hexagon, SolidCAM, CAMWorks, BobCAD, TopSolid and about 200 others. It does not say which partner uses which component ([ModuleWorks Partners](https://www.moduleworks.com/partners/)). The practical split follows. hyperMILL, NX, PowerMill and Tebis run in-house 5-axis engines. Mastercam reportedly combines native multiaxis with a ModuleWorks-derived suite, and an unofficial forum post says it shares that engine with GibbsCAM ([eMastercam](https://www.emastercam.com/forums/topic/91770-mastercam-and-gibbscam-use-the-same-5-axis-engine/)). Most of the mid-market buys its simultaneous 5-axis from ModuleWorks. Because so many products share one kernel, mid-market 5-axis strategy menus look alike. Vendors differentiate through automation, UX and verification.

## Fusion draws its paywall between positional and simultaneous motion

Fusion's tiers split on whether the rotary axes move *during* the cut. Core Fusion includes 3+1/3+2 positional milling ("4-axis wrapping of 2D toolpaths, align tool axis to view/surface normal, interactive tool axis tilt and turn"), machine simulation with a free machine library, mill-turn, WCS probing and the editable post library. The Extension holds the rest:

- all simultaneous 4/5-axis;
- multi-axis collision avoidance ("advanced tool axis smoothing, tool axis tilting limits");
- the automated 3-axis finishing set (Steep & Shallow, Deburr, Geodesic, Corner);
- automatic hole recognition and multi-axis drilling;
- toolpath modification and Replace Tool;
- geometry probing and 3/4/5-axis part alignment.

These all come from the official matrix ([Autodesk matrix via CAD Studio](https://cadstudio.cz/dl/fusion-manufacturing-extension-comparison-matrix-en.pdf)), and an Autodesk 2026 blog table repeats the split (search excerpt; [Autodesk](https://www.autodesk.com/products/fusion-360/blog/advanced-manufacturing-autodesk-fusion-manufacturing-extension/)).

| Capability | Personal (free, non-commercial) | Fusion (~$680/yr) | + Mfg Extension (~$1,465/yr) |
|---|---|---|---|
| 2D/2.5D, 3-axis milling, adaptive | Yes | Yes | Yes |
| 3+2 / 3+1 positional, 2D wrap | **No** | Yes | Yes |
| Simultaneous 4/5-axis (Rotary, Swarf, MA Contour, MA Flow, 5-axis S&S, MA Clearing) | No | No | Yes |
| Multi-axis collision avoidance / tilt | No | No | Yes |
| Steep & Shallow, Geodesic, Corner, Deburr | No | No | Yes |
| Auto hole recognition, toolpath editing | No | No | Yes |
| Machine simulation, editable posts | Yes (restricted output) | Yes | Yes |
| Rapids, tool changes in one program | **No** (rapids at feed; one tool per post) | Yes | Yes |
| Probing | No | WCS probing | + geometry probing, alignment |

The Personal column comes from Autodesk's personal-use page, which lists "2 & 3-axis milling, adaptive clearing, turning" and reserves "3+2 milling, 4 & 5-axis milling, mill-turning, set-up probing, automatic tool change, and rapid feed" for paid tiers (search excerpt; [Autodesk](https://www-pt.autodesk.com/in/products/fusion-360/personal)). Autodesk's FAQ (updated Feb 2025) confirms it ([Autodesk](https://autodesk.com/support/technical/article/Fusion-360-Free-License-Changes)). The open-source Batch Post add-in works around the one-tool-per-post limit and can restore G0 rapids experimentally ([GitHub](https://github.com/TimPaterson/Fusion360-Batch-Post)). The Extension cannot be bought for Personal use. Prices: core Fusion lists at $680/yr. The "Fusion for Manufacturing" bundle lists at $2,040 and is promoted at about $1,367 ([Autodesk](https://www.autodesk.com/campaigns/fusion-360/multi-seat-offer)). The Extension standalone price was cut from $1,600 to $1,465 in 2024 ([Autodesk](https://www.autodesk.com/products/fusion-360/blog/how-much-will-fusion-360-cost/)). The October 2026 US list price was not confirmed live.

**Autodesk is closing multi-axis gaps fast**, and a plugin must not plan around 2023-era weaknesses:

- **January 2026**: Multi-Axis Clearing (Extension). It does 3/4/5-axis roughing from floor/ceiling offsets, with Pocket or Adaptive styles and undercuts.
- **April 2026**: box-clearance linking geometry for multi-axis.
- **July 2026**: 3+2 Clearing. It uses multiple fixed orientations per operation and a virtual fixture. Its tier is unconfirmed.
- **September 2026**: Polar Machining links, 2-axis Part Alignment, and Geodesic "Straighten Cuts at Boundaries" ([release notes](https://help.autodesk.com/view/fusion360/ENU/?guid=FIC-REL-NOTES-INC)).
- **October 2026**: the `MachiningPlan` feature-recognition/planning API preview. It signals an automated-programming product feature.

User complaints on record skew old. They include B-axis wind-up and unwind on trunnions that buries the tool ([forum, ~2019](https://forums.autodesk.com/t5/fusion-manufacture-forum/re-5-axis-gurus-toolpath-example-request/m-p/8802224)) and a steep learning curve for tool-axis control. Getting rotary angles rather than vectors also requires a correct machine configuration in the post ([Autodesk](https://autodesk.com/support/technical/article/How-to-make-a-3-axis-post-processor-from-the-HSM-post-processor-library-support-4-or-5-axis-motion)). **Current 2025–26 user sentiment on Fusion multi-axis quality was not found** and should be gathered before committing to a feature set.

## The API automates native CAM but rejects foreign toolpaths

The `adsk.cam` API covers a lot. It walks CAM → Setups → Operations/Folders/Patterns. It creates setups and operations through `createInput(...)`/`add(...)` using a **strategy string**, and it sets tools, geometry and named parameters. It also does the following:

- generates toolpaths asynchronously (`generateToolpath` returns a `GenerateToolpathFuture`);
- posts with `postProcess`/`postProcessAll` and a `PostProcessInput`;
- writes HTML setup sheets ([CAM API intro](https://help.autodesk.com/cloudhelp/ENU/Fusion-360-API/files/CAMIntroduction_UM.htm)).

Machine kinematics have been scriptable since April 2023 through `Machine.create`, `LinearMachineAxisInput` and `RotaryMachineAxisInput` ([Machine.create](https://help.autodesk.com/cloudhelp/ENU/Fusion-360-API/files/cam_Machine_create.htm); [MachineAxis](https://help.autodesk.com/cloudhelp/ENU/Fusion-360-API/files/cam_MachineAxis.htm)). Tool and stock-material libraries are exposed as well ([CAM Libraries](https://help.autodesk.com/cloudhelp/ENU/Fusion-360-API/files/CAMLibraries_UM.htm)). October 2026 fixed add-ins being unable to put entries in the New Operation marking menu. Separately, the cloud **Fusion Automation API** (GA May 2025) runs Fusion scripts headless, including subtractive CAM, at 3.0 Flex tokens per processing hour ([APS](https://aps.autodesk.com/blog/design-automation-api-fusion-now-generally-available)).

Two limits define the design space. First, the strategy strings available come from `Operations.compatibleStrategies`, which "depend on license and extensions". **A plugin that drives native simultaneous strategies only works for Extension subscribers.** Second, Autodesk's API lead Brian Ekins has confirmed that custom toolpaths are "not currently possible" ([forum](https://forums.autodesk.com/t5/fusion-api-and-scripts-forum/ability-to-create-custom-toolpaths/td-p/10306786)). These statements are from around 2020–21, and **no 2025–26 change was found**. The third-party ecosystem fits this picture. Its add-ins cover feeds and speeds, tool libraries, verification connectors (Mazak, CAMplete TruePath), batch posting and automation. **No add-in that adds new simultaneous toolpath strategies inside Fusion was found.** Toolpath.com, the most sophisticated example, generates plans in its cloud and imports them as *native* setups and operations that "can be edited like any other Fusion program" ([Toolpath docs](https://docs.toolpath.com/cam-automation/how-to-export-machining-strategies-to-fusion)).

Three API questions remain open and decide the architecture. Each needs a check against the full `adsk.cam` reference or a prototype:

- whether an add-in can **read computed CL data** (points and tool vectors) from an operation;
- whether stock-simulation or collision results are exposed;
- whether a **Manual NC** operation can carry bulk motion rather than just labels and inserts. CAMplete maps Manual NC labels to custom G-code ([Autodesk help](https://help.autodesk.com/cloudhelp/2023/ENU/CAMTP-Fusion360/files/TPFusionManualNCtopicid.html)).

### Architecture options that follow from the constraint

| Option | Mechanism | Keeps native sim / NC program / posts | License dependency | Main risk |
|---|---|---|---|---|
| **A. Orchestrator** | Choose orientations, strategies, tools and parameters; create native ops via strategy strings, templates and `MachiningPlan` | Yes, fully | Value tracks the user's tier; simultaneous ops need the Extension | Head-on with Autodesk AI CAM, Toolpath, CloudNC; quality capped by native strategies |
| **B. Geometry supplier** | Compute drive curves and surfaces, boundaries, tilt points/curves, or orientation frames, then feed native Swarf, Flow, Project, Trace or 2D Contour | Yes | Simultaneous drivers need the Extension; 3+2 and 2D-wrap drivers work on core | Limited by what native strategies accept; edge behaviour stays with Autodesk |
| **C. Parallel engine** | Read BRep/mesh and machine definition via API; compute toolpaths externally; preview with custom graphics; simulate and post with own engine | No (own sim and post needed) | Works on core Fusion; possibly Personal (**legal review needed**) | Largest build; duplicates simulation and post; outside Fusion's NC program and setup sheets |
| **D. Hybrid** | Orchestrate natively where native ops suffice; fall back to C for strategies Fusion lacks; optionally hand G-code to an external verifier (CAMplete, ICAM, VERICUT) | Partly | Mixed | Two code paths to maintain; UX seams |

These options trade off integration against reach. Option A is the cheapest and best integrated, but it competes with Autodesk's announced roadmap and is pointless for users without the Extension. Option B is undervalued. Fusion's native Swarf and Flow are only as good as their drive geometry, and a plugin that computes good drive surfaces, tilt curves or orientation sets could add real intelligence while keeping native simulation and posting. Option C is the only route to features Fusion does not have at all, and the only route to users who don't pay for the Extension. Its cost is rebuilding most of the shared core described earlier: inverse kinematics, collision checking, linearization and a post. ICAM's Fusion kit shows the reverse direction already works. Fusion exports APT-CL through a special post, and an external post (GENER) and simulator (Virtual Machine) take over ([ICAM](https://help.icam.com/270/english/cam/kit/fusion360/readme)). That gives a precedent for G-code-level tooling that lives beside Fusion rather than inside it. A plugin that writes its own G-code on the Personal tier would technically sidestep the rapids and multi-axis limits. That is a **terms-of-use question for counsel**, not an engineering one.

## Open source covers 3-axis; 5-axis toolpaths must be built

The plugin is licensed **MIT OR Apache-2.0** (dual-licensed; the repository already carries this license). So the build-vs-license question is really a question of which code it may absorb, which it may only link against, and which it may only learn from. The answer is clear and somewhat constraining. Permissively licensed CAM code exists, mostly for 3-axis. LGPL libraries are usable only at arm's length. GPL projects are reference material at best. **No open, production-quality 5-axis toolpath library exists at all**, so the 5-axis core has to be written by the project.

### What the MIT OR Apache-2.0 license allows the plugin to reuse

| Tier | Projects | What the plugin may do | Practical use |
|---|---|---|---|
| **Permissive (MIT / Apache-2.0): use directly** | **Kiri:Moto / grid-apps** (MIT, very active, Oct 2026) ([GitHub](https://github.com/GridSpace/grid-apps)); **ROS-Industrial Noether** (Apache-2.0) ([GitHub](https://github.com/ros-industrial/noether)); **FiveAxisSimCore** (MIT, 5 stars) ([GitHub](https://github.com/li-yunwen/FiveAxisSimCore)); **Mas5ACAM** (MIT, 0 stars) ([GitHub](https://github.com/mallemann/Mas5ACAM)) | Copy, modify and vendor the code into the repo, keeping the copyright and license notices | Kiri:Moto's JS CAM (3-axis, indexed 4th, lathe-style rotary) fits Fusion's HTML/JS palettes. Noether's tool orientation on meshes informs 5-axis orientation work. FiveAxisSimCore (voxel/SDF) is a possible seed for a G-code simulator. Both 5-axis repos are young and need a full code review before adoption |
| **Weak copyleft (LGPL-2.1): separate, dynamically linked, replaceable dependency only** | **OpenCAMLib** (3-axis drop/push-cutter and waterline; Python/JS bindings; PyPI `opencamlib`) ([GitHub](https://github.com/aewallin/opencamlib)); **OCCT** (B-rep kernel, LGPL-2.1 + exception) ([OCCT](https://occt3d.com/open-cascade-technology/index.html)); **FreeCAD CAM** parts ([GitHub](https://github.com/FreeCAD/FreeCAD)) | Ship as unmodified (or separately published) libraries loaded at runtime, which users can swap out. Without a license the code is all-rights-reserved | At most, ask the authors to adopt MIT/Apache. Do not read for implementation detail, to keep the clean-room position safe |

Two practical points follow. First, Apache-2.0 includes an explicit patent grant, and dual licensing lets downstream users choose either license. Choosing MIT OR Apache-2.0 also keeps the door open for absorbing contributions from other permissive projects and for commercial forks. The cost is that GPL code stays permanently out of reach, and LGPL code can only be bundled as separate, replaceable binaries. Second, an LGPL dependency loaded from Fusion's embedded Python as a separate module fits the "replaceable library" model. That packaging should be documented, for example with a NOTICE/THIRD-PARTY file and instructions for swapping in a user-built OpenCAMLib.

### Proprietary dependencies the plugin cannot avoid

Even with an open-source codebase, the runtime is not open. **The Fusion API (`adsk.core`/`adsk.fusion`/`adsk.cam`) is proprietary**. The plugin can call it under Autodesk's terms but cannot redistribute it. Its CAM surface is also gated by the user's license tier through `compatibleStrategies` ([CAM API intro](https://help.autodesk.com/cloudhelp/ENU/Fusion-360-API/files/CAMIntroduction_UM.htm)). **Fusion's `.cps` post processors** are "free, editable" JavaScript ([matrix](https://cadstudio.cz/dl/fusion-manufacturing-extension-comparison-matrix-en.pdf)), but they run inside Autodesk's proprietary post engine. The redistribution terms of Autodesk's post library were not checked, so **do not vendor Autodesk `.cps` files into the repo [unverified terms]**. Machine-specific posts the project writes itself can be released under MIT/Apache, though they still need Autodesk's engine to run. A fully open path to G-code therefore needs the plugin's own post layer: inverse kinematics, rotary limits, unwinding, inverse-time feed, and controller dialects such as LinuxCNC and GRBL. That is the price of Option C. Options A and B stay inside Autodesk's pipeline and accept the proprietary posts.

### What the project must build itself

There is no open library to adopt for the 5-axis core. OpenCAMLib stops at 3-axis drop-cutter and push-cutter ([OCL docs](https://opencamlib.readthedocs.io/)). The open 5-axis repos are 2026 experiments with 0–9 stars. CAMotics simulates 3-axis only ([LinuxLinks](https://www.linuxlinks.com/camotics-3-axis-cnc-gcode-simulator/)). The project must write:

- tool-orientation planning (configuration-space approaches, [Springer IJAMT](https://link.springer.com/article/10.1007/s00170-023-12031-7));
- gouge and global collision detection (distance fields, BVH/OBB, GPU depth buffers [BK]);
- tilt-to-avoid and tool-axis smoothing;
- singularity and IK-branch handling;
- linearization and inverse-time feed;
- swarf deviation minimization;
- barrel-cutter contact math.

The Lasemi, Xue & Gu survey frames this problem set ([Manufacturing Review refs](https://mfr.edp-open.org/articles/mfreview/ref/2018/01/mfreview170023/mfreview170023.html)). This is the territory hyperMILL, NX, PowerMill and Tebis have spent decades on. The open-source strategy only works if scope is narrow: one family done excellently, not a full menu. Fusion's machine-definition API (`Machine`, `RotaryMachineAxis`, since April 2023) at least supplies kinematics to build against ([MachineAxis](https://help.autodesk.com/cloudhelp/ENU/Fusion-360-API/files/cam_MachineAxis.htm)). How much of it can be *read* (limits, offsets, head geometry) still needs verifying.

### Closed alternatives: ModuleWorks and MachineWorks, with trade-offs

Commercial kernels are the fallback, not the default. Each closed component the plugin links would split it into an open shell around a proprietary core. That conflicts with the open-source goal and would probably need a separately licensed build.

**ModuleWorks** is the only shelf-ready 5-axis toolpath library. It covers 3/4/5-axis machining, Automatic 3+2 Roughing, Adaptive and SmartRoughing, SuperFinish, FeedControl and VoluMill, plus a GPU/Machine Simulation SDK, Collision Avoidance System and Post Processor Framework. It releases about every four months ([ModuleWorks](https://www.moduleworks.com/)). It claims 200+ partners, including Autodesk Fusion itself ([Partners](https://www.moduleworks.com/partners/)). **No price list or startup program is public**; the only hint is a testimonial praising "flexible pricing… in the start-up phase". In 2023 **Autodesk and PTC took minority equity stakes** ([DE247](https://www.digitalengineering247.com/article/moduleworks-kicks-off-strategic-partner-program/cam)). That has two consequences. It would put the plugin on the same engine as the Extension it competes with, and ModuleWorks may want Autodesk's agreement first (speculative; ask ModuleWorks directly). Trade-off: strategy breadth on day one, against unknown cost, a closed core and partner politics.

**MachineWorks** is a verification and simulation SDK, not a toolpath library. It covers swept volumes, machine simulation, cutting analysis and Machine Builder kinematic trees. Its logos include Fusion 360, HSMWorks, Open Mind, SolidCAM, NCSIMUL, ICAM and IMS (vendor claim >60% of CAM developers; [MachineWorks](https://www.machineworks.com/customers)). Terms are not published. Trade-off: mature collision and material-removal simulation, against the same closed-core problem. An open voxel/SDF simulator (seeded from FiveAxisSimCore or written in-house) is the open-source alternative for G-code verification.

**Verification and post products to interoperate with rather than embed.** Shops expect G-code-level sign-off from one of these:

- **VERICUT 9.6**, with AI assistant and the Force physics-based feed optimization ([automation.com](https://www.automation.com/en-us/products/july-2025/cgtech-announces-vericut-9-6));
- **NCSIMUL**, with GPU selective simulation added May 2026 ([Hexagon](https://hexagon.com/company/newsroom/press-releases/2026/hexagon-helps-manufacturers-verify-and-optimise-nc-programs-faster-with-ncsimul));
- **CAMplete TruePath**, with its reported end of sale above;
- **ICAM Virtual Machine/CAM-POST**, which has official Fusion 2021–2025 support through APT-CL export ([ICAM](https://help.icam.com/270/english/cam/kit/fusion360/readme));
- **IMSverify**;
- **Roboris Eureka**, licensed into SolidCAM.

A VERICUT–Fusion or NCSIMUL–Fusion interface was not confirmed. An open plugin can export to these through standard G-code or APT-CL without any licensing entanglement. On Fusion's own post engine, the API exposes `MachineConfiguration.getABCByPreference`, `optimizeMachineAngles2` and inverse-time output ([MachineConfiguration](https://cam.autodesk.com/posts/reference/classMachineConfiguration.html); [forum](https://forums.autodesk.com/t5/hsm-post-processor-forum/multi-axis-feedrates/m-p/7346609)). Sources conflict on what `optimizeMachineAngles2` mode 0 versus 1 means ([forum](https://forums.autodesk.com/t5/hsm-post-processor-forum/fanuc-5x-no-a-c-indexing/m-p/7354454)). Even default posts sometimes need modification for true simultaneous 5-axis ([UiTM thesis](https://ir.uitm.edu.my/id/eprint/37755)).

## Five openings remain once Autodesk's 2026 roadmap is subtracted

**1. Collision-free automatic tilting that users can understand.** Automatic tool-axis management is where the leaders compete in 2026: hyperMILL's Minimum Clearance Angle and automatic orientation, Mastercam's auto tilt, PowerMill's Automatic Tool Tilting, and Tebis's simultaneous-avoidance roughing. It is also where the research literature is most active. Fusion's Extension has collision-avoidance tilting, but no source rates it against the leaders. A plugin that makes tilting **explainable** would occupy the hardest and most valuable slice. That means showing a reachability or accessibility map before programming, showing why each tilt was chosen, and showing minimum tool stick-out, all aware of holder, fixture and machine head. This "explainable" pain point is an inference, not a sourced complaint. Delivered via Option B (orientation and tilt-curve geometry feeding native ops), it stays inside Fusion's simulation and post. Delivered via Option C, it reaches core-tier users.

**2. Affordable continuous 4-axis and small-machine 5-axis.** Hobby and prosumer rotary users are stuck with wrap-only tools (Vectric, Makera) or index-only tools (MeshCAM, Kiri:Moto, DeskProto). Kiri:Moto users ask for spiral rotary cutting. Fusion Personal blocks even 3+2. Prosumer 5-axis machines such as the Pocket NC V2-8Lite ($4,900; [All3DP](https://all3dp.com/4/penta-machine-company-announces-pocket-nc-v2-8lite-desktop-cnc-machine/)) are programmed in Fusion ([Pentamachine](https://pentamachine.atlassian.net/wiki/spaces/PNFUR/pages/1727037445)). For these buyers the Extension's $1,465/yr is a large share of the machine's price. This segment needs:

- correct trunnion kinematics;
- simple fixture models;
- winding and unwinding control;
- inverse-time feed;
- LinuxCNC/GRBL rotary posts.

The open questions are legal (Personal-tier terms) and commercial. Onshape CAM Studio Advanced is announced but unshipped, and the segment's size is unquantified.

**3. Application packs that Fusion does not have.** Port, impeller/blisk, blade and tube machining are paid modules in hyperMILL, NX, Mastercam and PowerMill [BK], and SolidCAM ships port and multi-blade. **No Fusion equivalent was found** [unverified]. Autodesk's own answer to heavy 5-axis is "Fusion + PowerMill", and PowerMill's 2026 release was maintenance-only. Shops migrating off HSMWorks (end of life 2028), Inventor CAM and possibly FeatureCAM are a natural audience. These packs are geometry-specific enough that a focused team can build one well, and Option C or D is the only way to deliver them in Fusion.

**4. G-code-level verification and post validation inside the Fusion ecosystem.** Posts are the most-cited failure point in multi-axis work. Fusion's simulation runs on CL data, not on posted G-code. If CAMplete's reported end of sale (June 2026) is accurate, Autodesk's own G-code verifier for Fusion is leaving the market [unverified]. VERICUT and NCSIMUL are expensive standalone products. A Fusion add-in that does three things would fill a real gap with a modest algorithmic burden compared with toolpath generation:

- simulate posted G-code against Fusion's machine definition, catching axis-limit violations, unwinding errors and singularity flips;
- validate `.cps` machine configurations;
- report the result clearly.

A permissively licensed voxel/SDF starting point exists (FiveAxisSimCore, MIT), so this opening also fits the open-source license best. MachineWorks is the closed alternative.

**5. Physics-aware multi-axis feeds and AI strategy selection.** Engagement-based feed control is now a kernel feature (ModuleWorks FeedControl, VoluMill) and a verification feature (VERICUT Force). In Fusion it is reached only through feeds-and-speeds add-ins. AI-assisted *multi-axis* strategy selection is open ground, because shipping AI tools stop at 3-axis and 3+2. Both are secondary bets, since Autodesk's AU 2026 AI CAM announcement could extend into them.

**What to avoid** is just as clear. Re-implementing 3-axis strategy families adds nothing; Fusion core already has them. Automated 3-axis and 3+2 programming is crowded: Autodesk's native AI CAM and `MachiningPlan`, the Autodesk-backed Toolpath, CloudNC's 1,000+ shop install base, and 3+2 Clearing all compete there. Any feature that matches Multi-Axis Clearing, box-clearance linking or polar links will be judged against free updates to software the user already pays for.

### Recommended open-source-first path under MIT OR Apache-2.0

The license choice and the openings point the same way. The best-sequenced plan builds the parts that open source lacks and that Autodesk is not shipping, in an order where each stage is useful by itself.

**Stage 1 is a kinematics and verification foundation**, covering openings 4 and 2. Read the machine definition through the Fusion API. Then write an MIT/Apache inverse-kinematics and forward-kinematics solver for table-table, head-table and head-head machines, and a G-code simulator, seeded from or modelled on FiveAxisSimCore. The simulator should detect axis-limit, unwinding and singularity faults, plus gross collisions, on posted code from *any* Fusion tier. The same IK layer becomes the core of an open post layer for LinuxCNC/GRBL rotary output. Autodesk `.cps` files are left untouched and unvendored.

**Stage 2 is orientation and tilt intelligence delivered as geometry (Option B)**, covering opening 1. Compute reachability maps, 3+2 orientation sets, tilt points and curves, and swarf/flow drive surfaces. Write them into the Fusion document as sketches, surfaces and setups that native operations consume, so native simulation and posting keep working. Kiri:Moto (MIT) can contribute JS geometry utilities. OpenCAMLib, as an optional, separately installed LGPL wheel, can supply 3-axis drop-cutter queries for gouge checks.

**Stage 3 is a narrow parallel engine (Option C)**, covering openings 2 and 3. Add in-house continuous 4-axis and one application family (port machining is the smallest well-bounded candidate), posted through the Stage 1 post layer. This is the only stage that reaches non-Extension users, and the Personal-tier terms question must be resolved before it targets that tier.

Throughout, keep a `third_party/` boundary and a NOTICE file listing every MIT/Apache inclusion with its original notices. Keep LGPL components out of the source tree as runtime dependencies users can replace. Use GPL code only as reading for clean-room work. Do not read OpenMill or collet internals until their authors license them, and consider inviting them to adopt MIT/Apache, since their claimed strategy sets overlap Stage 3. ModuleWorks or MachineWorks should be considered only if Stage 3 scope demands breadth the project cannot build. Even then they belong in a separately licensed build, so the MIT/Apache core stays fully open.

## Conclusion

The landscape inverts the usual plugin logic. In Fusion, building toolpath strategies is the *least* leveraged move, because the API cannot slot them in natively, the Extension already ships the standard set, and Autodesk's 2026 cadence keeps narrowing what remains. The leverage is on either side of the strategy: upstream, in deciding orientations, tilts, drive geometry and reachability; and downstream, in proving that posted code is safe on a specific machine. Both can be built as open-source MIT/Apache code without ModuleWorks, which is exactly where the open-source ecosystem is emptiest. Both reuse Fusion's machine definitions, and both match where the leaders compete (automatic tool-axis management) and where users get hurt (posts and verification). A full parallel engine is justified only for capabilities Fusion lacks entirely, such as application packs or continuous 4-axis for non-Extension users, and only once the open API questions (CL read access, Manual NC payloads, Personal-tier terms) are settled.

The decisive near-term step is a prototype spike, not more market research. It should confirm three things: what an add-in can read back from a generated operation, what it can push into native Swarf, Flow and Project as drive geometry, and how much of the machine kinematic model is readable. Those answers will decide between Options B, C and D more than any competitor feature does. The open-source license turns a weakness into positioning. No open 5-axis toolpath or verification library exists, so a well-built MIT/Apache kinematics, simulation and orientation core would be the first of its kind and reusable well beyond Fusion. That would attract contributors from the LinuxCNC, FreeCAD and prosumer-machine communities, who currently believe "there is no free 5 axis software". The residual strategic risk is dependence on Autodesk's proprietary API and roadmap. That argues for keeping the core host-agnostic and treating Fusion as the first adapter rather than the only one.
